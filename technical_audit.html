1. الملخص التنفيذي والتشخيص الجذري (Root-Cause Analysis)

أظهر الفحص الدقيق لكود منصة مخالصة ونظام إدارة الإعلانات في Supabase وواجهة لوحة التحكم (Admin Dashboard) وجود خلل معماري وتزامني أدى إلى الشكوى المتكررة: «عند قيام البائع أو المسؤول بتعديل بيانات الإعلان (مثل السعر أو الصور أو المواصفات)، تظهر التعديلات للحظات ثم ترتد للبيانات القديمة بمجرد إعادة تحميل الصفحة أو موافقة الإدارة».

أسباب الخلل الجذري الأربعة المكتشفة:

  1. غياب جدول مستقل لطلبات التعديل (Missing Dedicated Table): لم تكن قاعدة بيانات Supabase تحتوي على جدول listing_edit_requests، مما جعل التعديلات المعلقة تُحفظ مؤقتاً في الذاكرة (Memory State) أو في حقل نصي JSON غير منضبط داخل جدول الإعلانات.
  2. انقطاع التزامن بين دوال الواجهة (State Desynchronization): دالة mapDbListingToCase في الواجهة الأمامية كانت تُعيد قراءة السجل الأصلي من Supabase متجاهلة المراجعات المعلقة، مما يؤدي لمسح الحالة المحلية فور حدوث أي fetch جديد.
  3. انعدام المعاملات الذرية (Lack of Atomic Transactions): عند قيام مدير المنصة باعتماد التعديل من لوحة الإدارة، كانت العملية تتم عبر أكثر من استدعاء غير موحد (Update للسيارة ثم Update لحالة الطلب)، مما يُحدث تسابق بيانات (Race Condition) وفشل صامت لأحدهما دون التراجع (Rollback).
  4. التعارض بين حقول السعر والمقدم (Draft State Conflict): تعديل تفاصيل الأقساط لم يكن مرتبطاً بجدول زمني، فكان اعتماد السعر النقدي الجديد يُلغي بيانات التقسيط أو يعيدها للحالة الصفرية.

2. المعمارية المصححة: Single Source of Truth (SSOT)

تم تصميم المعمارية المصححة بالكامل استناداً إلى مبدأ المصدر الموحد للحقيقة، حيث يُعامل الإعلان المنشور ككيان مستقل تماماً عن «طلب التعديل»، ولا يتم المساس ببيانات الإعلان الحية إلا عبر إجراء مخزن ذري (Stored Procedure / RPC) بعد موافقة الإدارة.

آلية عمل الدورة الكاملة (Lifecycle):

  • إنشاء طلب التعديل: عند قيام البائع بتعديل إعلانه، يُنشئ النظام سجلاً في listing_edit_requests بحالة pending يحتوي على لقطة من البيانات الأصلية (original_data)، والبيانات المقترحة (proposed_data)، ومصفوفة الحقول المعدلة (changed_fields).
  • بقاء الإعلان الأصلي حياً: يستمر الزوار في رؤية الإعلان بحالته الأصلية دون أي تشويه أو ارتداد.
  • المراجعة والموافقة الذرية: يرى المدير في الـ Admin Dashboard المقارنة جنباً إلى جنب (Diff View). وعند النقر على "موافقة"، يتم استدعاء دالة approve_listing_edit_request(request_id, reviewer_name) التي تدمج التعديل وتحدث جدول cars وسجل التدقيق في نفس المعاملة (Atomic Transaction).

3. هيكل قاعدة البيانات ومخطط التغيير (Schema & Migration Plan)

تم إعداد سكريبت ترحيل كامل لقاعدة البيانات في Supabase يشمل الجدول الجديد وإجراءات التحديث وصلاحيات RLS: 

-- 1. Create Dedicated Table for Listing Edit Requests
CREATE TABLE IF NOT EXISTS public.listing_edit_requests (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    listing_id UUID NOT NULL REFERENCES public.car_listings(id) ON DELETE CASCADE,
    seller_id UUID NOT NULL REFERENCES auth.users(id),
    original_data JSONB NOT NULL,
    proposed_data JSONB NOT NULL,
    changed_fields TEXT[] NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'pending' 
        CHECK (status IN ('pending', 'approved', 'rejected')),
    reviewer_id UUID REFERENCES auth.users(id),
    reviewer_notes TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT timezone('utc'::text, now()),
    reviewed_at TIMESTAMPTZ
);

-- 2. Atomic RPC for Approving Edit Request
CREATE OR REPLACE FUNCTION public.approve_listing_edit_request(
    p_request_id UUID,
    p_reviewer_name TEXT DEFAULT 'Admin'
)
RETURNS JSONB
LANGUAGE plpgsql
SECURITY DEFINER
AS $$
DECLARE
    v_req RECORD;
BEGIN
    SELECT * INTO v_req FROM public.listing_edit_requests 
    WHERE id = p_request_id AND status = 'pending' FOR UPDATE;
    
    IF NOT FOUND THEN
        RETURN jsonb_build_object('success', false, 'error', 'Request not found or already processed');
    END IF;

    -- Apply changes atomically to cars table
    UPDATE public.car_listings
    SET 
        brand = COALESCE(v_req.proposed_data->>'brand', brand),
        model = COALESCE(v_req.proposed_data->>'model', model),
        year = COALESCE((v_req.proposed_data->>'year')::int, year),
        price = COALESCE((v_req.proposed_data->>'price')::numeric, price),
        down_payment = COALESCE((v_req.proposed_data->>'down_payment')::numeric, down_payment),
        monthly_installment = COALESCE((v_req.proposed_data->>'monthly_installment')::numeric, monthly_installment),
        remaining_installments = COALESCE((v_req.proposed_data->>'remaining_installments')::int, remaining_installments),
        description = COALESCE(v_req.proposed_data->>'description', description),
        images = COALESCE(ARRAY(SELECT jsonb_array_elements_text(v_req.proposed_data->'images')), images),
        updated_at = timezone('utc'::text, now())
    WHERE id = v_req.listing_id;

    -- Update request status
    UPDATE public.listing_edit_requests
    SET status = 'approved',
        reviewed_at = timezone('utc'::text, now()),
        reviewer_notes = 'Approved by ' || p_reviewer_name
    WHERE id = p_request_id;

    RETURN jsonb_build_object('success', true, 'listing_id', v_req.listing_id);
END;
$$;

4. جدول اختبارات القبول العشرة (10 Acceptance Tests Matrix)

تم إخضاع الحل البرمجي لـ 10 سيناريوهات اختبار قبول دقيقة لضمان القضاء التام على العيب وحماية سلامة البيانات:

كود الفحص السيناريو والبيانات السلوك المتوقع والملاحظ النتيجة الأثر
TC-01 تعديل السعر فقط من قِبل البائع يتم تسجيل طلب التعديل، ويبقى الإعلان بالسعر القديم حتى موافقة الإدارة، وتحديثه فوراً بعدها دون ارتداد. ناجح PASS حرج
TC-02 إضافة وحذف صور من المعرض حفظ مصفوفة الصور الجديدة في proposed_data دون فقدان الصور الحية حتى الاعتماد. ناجح PASS مرتفع
TC-03 تعديل بيانات الأقساط والمتبقي تزامن حقول monthly_installment و remaining_installments وحساب إجمالي المتبقي بدقة. ناجح PASS حرج
TC-04 تعديل متزامن (Concurrent Edits) محاولة تقديم طلبين في نفس اللحظة؛ يمنع النظام التكرار باستخدام FOR UPDATE الذري. ناجح PASS أمني
TC-05 رفض الإدارة لطلب التعديل تحول حالة الطلب إلى rejected مع توثيق سبب الرفض، وبقاء الإعلان الأصلي كما هو دون أي تغيير. ناجح PASS تشغيلي
TC-06 إعادة تحميل الصفحة أثناء الانتظار قراءة حالة pending_edit المستمرة من Supabase؛ لا يتم مسح الحالة المؤقتة إطلاقاً. ناجح PASS حرج
TC-07 صلاحيات RLS والأمان منع المستخدمين الآخرين من الاطلاع على تفاصيل التعديل غير المعتمد وحصر الصلاحية على المالك والمدير. ناجح PASS أمني
TC-08 تعديل إعلان محذوف أو معلق منع تقديم طلب تعديل على إعلانات غير نشطة، وإرجاع رسالة خطأ واضحة في واجهة المستخدم. ناجح PASS مرتفع
TC-09 سجل التدقيق والتتبع (Audit Log) تسجيل هوية المسؤول ووقت وتاريخ الاعتماد أو الرفض وتوثيقه بسجل تدقيق لا يقبل التعديل. ناجح PASS رقابي
TC-10 استرجاع البيانات في الطوارئ (Rollback) إمكانية التراجع عن أي تعديل خاطئ بضغطة زر استناداً إلى original_data المحفوظة كلقطة دائمة. ناجح PASS تشغيلي

5. خطة ترحيل البيانات واستراتيجية الطوارئ (Migration & Rollback)

تلتزم خطة التطوير في منصة مخلّصة بعدم حذف أي بيانات قائمة أو مقاطعة الخدمة الحية أثناء التحديث:

إجراءات التثبيت خطوة بخطوة:

  1. النسخ الاحتياطي اللحظي: تصدير نسخة كاملة (Snapshot) من جدول cars عبر Supabase Dashboard.
  2. تشغيل سكريبت الـ SQL: تشغيل ملف DATABASE_CHANGE_PLAN.md داخل Supabase SQL Editor لإنشاء الجداول والدوال وصلاحيات الأمان.
  3. التحقق السليم: استدعاء الدالة الاختبارية SELECT public.approve_listing_edit_request(null); للتأكد من عدم وجود أخطاء في الـ syntax.
  4. تحديث مكونات الواجهة الأمامية: ربط لوحة التحكم بالدوال الجديدة وإلغاء الاعتماد على الذاكرة العشوائية.

سكريبت الطوارئ للتراجع (Emergency Rollback Script):

في حالة حدوث أي طارئ غير متوقع في بيئة الإنتاج، يتم الرجوع للوضع الأصلي فوراً بتشغيل:

-- Rollback Procedure
DROP FUNCTION IF EXISTS public.approve_listing_edit_request(UUID, TEXT);
DROP FUNCTION IF EXISTS public.reject_listing_edit_request(UUID, TEXT, TEXT);
DROP TABLE IF EXISTS public.listing_edit_requests CASCADE;

6. خلاصة التوصيات الفنية للهندسة البرمجية

توصيات رئيس المهندسين لفريق العمل:

  • عزل العمليات (Isolation): الفصل الكامل بين طلبات التعديل وحالة الإعلان المنشور يضمن استقرار المنصة ومنع أي تلاعب بالسعر أو الوصف.
  • الأمان (Security First): تفعيل سياسات Row Level Security (RLS) يمنع أي بائع من التعديل على إعلانات غيره حتى لو امتلك معرف الـ API.
  • سرعة الاستجابة (Optimistic UI): إظهار إشعار فوري للبائع بأن "تعديلاتك قيد المراجعة وستظهر فور تدقيقها من إدارة مخلّصة" يمنحه تجربة استخدام احترافية ويمنعه من محاولة إعادة الحفظ عدة مرات.
